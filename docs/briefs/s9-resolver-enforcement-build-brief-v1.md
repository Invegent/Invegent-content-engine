## Scope

**In scope:**
- One classifier call inserted at **Layer 1** (`m.fill_pending_slots`, before its existing format-assignment logic) per architecture packet §2.1.
- One classifier call inserted at **Layer 2** (`ai-worker`, immediately before the single write site that finalizes `recommended_format` — main path and evergreen path both), per §2.1.
- The blocked-state write contract exactly as specified in §2.1/§4: `requested_format` preserved unconditionally; `recommended_format` left unset/null on block (never substituted); `final_format_authority = 'blocked_by_capability'`; `final_format_reason` = the classifier's own `status`/`reason_code`/evidence verbatim; **never** touching `video_status`, `approval_status`, or any publish-failure status.
- Fail-closed semantics: an RPC error/timeout from the classifier is treated as not-ready, never silently as Ready.
- **Layer 1 non-ready handling — DECIDED (PK ruling, 2026-07-29): skip-with-reason via the existing `cc-0019`-gate pattern already live in `m.fill_pending_slots`, NOT allow-list re-pick.** On a non-ready candidate: (a) write the slot-fill-attempt evidence (`INSERT INTO m.slot_fill_attempt` with `decision='skipped'`, `skip_reason='capability_blocked:<requested_format>'`, mirroring the existing gate's own INSERT shape); (b) `UPDATE m.slot SET status='skipped', skip_reason='capability_blocked:<requested_format>', updated_at=NOW()`; (c) append the standard per-slot result object to the function's return; (d) `CONTINUE` — stop processing that slot, no draft, no `ai_job`, no token spend. **Do not re-pick, substitute, or fall back to another format at this layer** — this preserves the schedule's desired format as demand and prevents silent substitution, per PK's explicit ruling. The insertion point is the same structural position as the existing `cc-0019` `is_publish_eligible` gate (early in the per-slot loop, before any pool/evergreen query) — confirmed live and reusable, not a new pattern invented for this brief (`db-rls-auditor` retrace, 2026-07-29).
- **Per-slot fault isolation for the Layer 1 call — REQUIRED (specialist DB review finding, 2026-07-29, must-fix; scope tightened after external review, 2026-07-29).** `m.fill_pending_slots` processes up to 5 slots per invocation inside **one transaction**. `classify_format_capability` is materially more complex than the existing boolean `is_publish_eligible` check (composes `select_template` + `resolve_slot_assets`, jsonb/array work) and is not proven exception-free. The Layer 1 call **must** be wrapped in its own `BEGIN ... EXCEPTION WHEN OTHERS` block: on an unhandled exception, treat it identically to a non-ready classification (skip that slot only, `skip_reason='capability_check_error'`, per the same fail-closed principle already governing an RPC error/timeout) — **never let a classifier exception abort the whole batch transaction and roll back other, already-filled slots** (potentially other clients' work in the same cron tick). Two constraints on how this must be built, not just that it exists: **(a) the exception handler must wrap ONLY the `classify_format_capability` call itself**, not the slot's surrounding processing logic — a blanket catch around more code than necessary would silently hide unrelated bugs elsewhere in the loop, which is a new risk this fix must not introduce; **(b) the caught exception's `SQLSTATE`/`SQLERRM` must be captured into the skip evidence** (e.g. appended to `skip_reason` or logged via `RAISE WARNING` with the slot/client identifiers), not silently swallowed — so a real, recurring classifier defect remains observable (e.g. via a dashboard/log query) rather than permanently indistinguishable from an expected non-ready classification. This is a hardening of "fail-closed on RPC error," not a new principle — it closes a gap the architecture packet's fail-closed language didn't explicitly extend to unhandled exceptions vs. graceful non-ready returns.
- **`client_id` → `client_slug` resolution — REQUIRED (specialist DB review finding, 2026-07-29, must-fix).** `classify_format_capability` takes `p_client_slug text`; `m.fill_pending_slots` operates entirely on `v_slot.client_id` (uuid) today, with no existing slug lookup anywhere in the function. The Layer 1 edit must add a `client_slug` resolution (e.g. `SELECT client_slug FROM c.client WHERE client_id = v_slot.client_id`) before the classifier call — this was missing from the original design and is now an explicit build requirement, not left implicit.

## Rollback boundary (exact, per PK ruling 5)

Both edits in this brief are `CREATE OR REPLACE FUNCTION` (no table DDL), so rollback is a function-body revert, not a data migration:

- **Layer 1 (`m.fill_pending_slots`):** rollback = `CREATE OR REPLACE FUNCTION m.fill_pending_slots(integer)` restoring the pre-change body captured by this build's own backfill migration (the live body pulled fresh before editing, per Success criteria). No `m.slot`/`m.slot_fill_attempt` row needs to be reverted — a slot that was skipped with `skip_reason='capability_blocked:<format>'` before rollback simply stops receiving new skips of that kind after rollback; already-written rows are historical fact, not undone (consistent with every other `skip_reason` code in this table, none of which are ever retroactively cleared).
  - **Safety under concurrent cron execution (evidence, not an unstated assumption — raised by external review, 2026-07-29):** `m.fill_pending_slots` runs every 10 minutes via `cron.job` (jobid 75, confirmed live by the specialist DB review). PostgreSQL resolves a `plpgsql` function's compiled body at the start of each individual call; `CREATE OR REPLACE FUNCTION` takes a brief catalog lock but does not alter or abort a call already in progress — an in-flight invocation from a tick that started before either the forward change or the rollback completes runs to completion on whichever body it started with, and the *next* tick (at most ~10 minutes later) picks up the new definition. There is no partial-execution or mixed-body risk. This applies identically to the forward deploy and the rollback — neither requires pausing the cron job, though the deploy plan for PK gate 2 should still name the cron job explicitly and confirm this reasoning against the live scheduler entry immediately before either action, as ordinary production-change hygiene rather than because a special risk is suspected here.
- **Layer 2 (`ai-worker`):** rollback = redeploy the prior `ai-worker` version (version-bump revert), restoring the unconditional `recommended_format` write.

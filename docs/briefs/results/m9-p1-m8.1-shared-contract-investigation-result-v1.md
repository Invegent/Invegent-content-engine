**4.5 Verdict (task 3): DISPROVEN — two independent contracts, not one shared source.**

- **Contract 1 — governance-enablement (M8.1's need):** `c.client_creative_governance` via `get_client_creative_governance(p_client_slug)`. **(client, format)** grain only — **no platform dimension exists in the source table**, so M8.1's own brief wording ("per client, platform, format") overstates what this table can actually differentiate; the badge can only be as platform-specific as the *other* signals it combines this with. - **Contract 2 — capability/ladder state (P-1's need):** `classify_format_capability` via `get_client_production_readiness_queue(p_client_slug)`. **(client, platform, format)** grain, real asset-pool-depth fields (`declared_asset_pool_count`, `resolver_reachable_asset_count`, `minimum_required_pool`), real ladder-position fields (`capability_status`, `missing_proof_or_gate`, `responsible_lane`). There is nothing to name as "the exact source/shape both implementations must consume" because no single source covers both needs — implementation (if authorized later) is two independent wiring jobs, not one shared contract.

- When a brief says two features share a "topical connection" (both brief authors here explicitly flagged this as unconfirmed, see the M9-P1/M8.1 brief's own Open Question 2), reading the actual migration/RPC bodies in full — not just their names or comments — is what actually settles whether they share a data source.

## 0. Authoritative backend meaning of `scheduled_demand` (established before any code change)

**Static source (`invegent-content-engine`,
`supabase/migrations/20260730120000_client_production_readiness_queue_rpc_v1.sql`):**

- Line 320: `NOT ac.is_probe_cell AS scheduled_demand` — a genuine SQL boolean, never a count.
- Lines 60-68 (header comment): "Any of the 4 named platforms with ZERO cell from
  (a)/(b)/(c) [allocator-active cells / format-override slots / materialised slots] gets exactly
  ONE synthetic PROBE cell... Probe cells carry `scheduled_demand=false` and `is_probe_cell=true`
  so they are never mistaken for real requested demand."
- Lines 258-278: the CTE chain confirms `is_probe_cell=false` for every row sourced from real
  config/override/slot cells, and `true` only for the synthetic per-platform probe branch.
- Grants (lines 664-667): `EXECUTE` revoked from `PUBLIC`/`anon`/`authenticated`, granted to
  `service_role` only — the field itself carries no new REST-exposure/grant risk; this was
  purely a dashboard-side typing/parsing defect, not a backend or security issue.

**Conclusion:** `scheduled_demand` means *"this (platform, format) cell reflects real
config/override/slot demand, as opposed to being a synthetic probe cell inserted only to
surface an otherwise-unconfigured platform."* It is a per-cell boolean flag, not a count of
anything. No separate count field exists or was needed for this task's scope.

**Live confirmation (this lane, direct `execute_sql` read against project
`mbkmaxqhsohbtwsqolns` — the same project the dashboard reads):**

```sql
select
  jsonb_typeof(cell->'scheduled_demand') as scheduled_demand_type,
  cell->'scheduled_demand' as scheduled_demand_value,
  count(*) as n
from c.client c
cross join lateral jsonb_array_elements(public.get_client_production_readiness_queue(c.client_slug)) as cell
group by 1, 2
order by 1, 2;
```

Result, across **every client currently in `c.client`** (76 total (platform, format) cells):

| scheduled_demand_type | scheduled_demand_value | n  |
|---|---|---|
| boolean | true | 76 |

**100% of live cells return a native JSON boolean, zero exceptions, zero numbers, zero strings.**
A per-cell breakdown for `property-pulse` / `care-for-welfare-pty-ltd` / `invegent` (45 of the 76
cells) additionally confirmed `is_probe_cell=false` paired with `scheduled_demand=true` on every
one of those rows, both typed `boolean`. **No live probe cell (`is_probe_cell=true`) exists for
any client at this moment** — every platform for every current client has at least one real
config/override/slot cell, so the `false` branch of `scheduled_demand` is not currently
observable live. That branch is evidenced instead by (a) the migration's own CTE logic cited
above (lines 258-278, the probe-cell construction is unconditional and structural, not
data-dependent) and (b) the already-shipped `tests/production-readiness-queue.test.ts` fixture
(`is_probe_cell: true` / Care for Welfare YouTube proof case, predates this lane) — named
honestly here rather than fabricating a live `false` row that does not currently exist.

This closes the loop the M8 result doc's §0 left open (that doc observed the field
"boolean/boolean-string" without a same-query `is_probe_cell` pairing or raw JSON) — one
same-query read, both fields, per cell, decoded type included, superseding that earlier
observation with typed live evidence.

## 9. Learning notes (chat fills this)

- **A subagent invocation can silently lack tools its own team-table entry says it should have**
  — the first `db-rls-auditor` call for this lane reported (correctly, not fabricated) that it
  had no `execute_sql`/`get_advisors` bound and no read-only DSN, even though `db-rls-auditor` is
  documented as carrying exactly those tools. Worth flagging for whoever maintains the agent
  registry: confirm tool-binding consistency, don't assume the team-table description matches
  every invocation. The orchestrator's own direct Supabase MCP access was the correct fallback
  here, not a workaround to route around the gap.
- **Reusable pattern:** when a shared boolean field already has sibling fields parsed with the
  same helper in the same file (here, `asBoolOrNull` already used for `platform_pause_state.active`,
  `publisher_readiness.ready`, `runtime_reachable`, `is_probe_cell`), retyping a mistyped field to
  match that existing helper — rather than inventing new parsing logic — is both the smaller diff
  and the more consistent fix. Worth naming as a standing check whenever a "field X is mistyped"
  defect is found: look for a sibling field in the same file using the correct parser first.
- **The bounded-lane shape worked as intended:** a defect logged at M8 closeout, scoped to
  exactly the file set that needed to change, closed same-day without touching schedule rows,
  readiness semantics, or Asset Gap backend data — the discipline M8's own scope fence
  (§5/§6/§7) was designed to enable as a fast, safe follow-on.

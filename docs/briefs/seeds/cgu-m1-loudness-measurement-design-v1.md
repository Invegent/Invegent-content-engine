## 1. Current state (what exists today)

- **Presence-only gate is LIVE**, not loudness. `video-worker` v3.14.0 added `mp4HasAudioTrack` — a byte scan of the already-fetched render buffer for the ASCII `'soun'` hdlr handler_type — which fails a voiced/music render CLOSED if the mp4 has literally no audio stream (`supabase/functions/video-worker/index.ts:162-194`). This is a **container-level presence check**, not a loudness measurement.
- **The code says why, explicitly, in production comments**: `supabase/functions/video-worker/index.ts:171` — *"ffmpeg cannot run in an Edge Function, so this is a byte/spec heuristic; a true integrated-LUFS probe (Phase B) is a SEPARATE later lane, DEFERRED here."* This is the authoritative, current-HEAD confirmation that an in-EF ffmpeg port is not viable in the Deno Edge Function runtime — not a hypothesis, a documented constraint the presence-only gate was deliberately built around.
- **The QA layer already reserves the field.** `supabase/functions/video-worker/qa.ts:17-19` (byte-identical to `heygen-worker/qa.ts`, `qa.ts:14-15`) lists `loudness_lufs` verbatim under `DEFERRED (NOT computed here, by design — no probing/re-fetch)`. The target field name in the acceptance criterion (`render_spec.qa.loudness_lufs`) is not new — it is the field this module already named and left unset.
- **`qa.ts` is a hard-constrained pure module**: no side effects, no `Deno.serve`, no provider/network/DB/storage call, byte-identical across two worker directories (`qa.ts:3-8,14-15`). Any byte-inspection or external call MUST happen in the worker (which holds the render buffer) and be **passed into** `buildRenderQa` as a new input field — never computed inside `qa.ts`. This is a hard constraint, not a preference.

## 2. The offline harness tool (found + cited, per the task)

`_harness/audio_gate_v0/audio_gate.py` is the tool the delta-audit row means by *"true LUFS measurement exists only as an offline harness tool, never wired to a live render"* (`...delta-audit-v1.md:390`).

- **Mechanism**: Python CLI, resolves `ffmpeg` via the `imageio_ffmpeg` PyPI package (no arbitrary-binary download — same sourcing already used for the 2A numeric-audio proof, `docs/briefs/results/creatomate-video-breadth-2a-numeric-audio-v1.md:5`). Runs `ffmpeg -af loudnorm=I=-14:TP=-1:LRA=11:print_format=json -f null -` and parses the `input_i` (integrated LUFS) / `input_tp` (true peak dBTP) JSON block from stderr (`audio_gate.py:52-64`).
- **Fail-closed by construction**: no audio stream, unparseable measurement, `-inf`/non-finite loudness, or any exception → `FAIL`, never a silent `PASS` (`audio_gate.py:8-11,75-100`). Default floor `-40 LUFS`, CLI-overridable (`audio_gate.py:14,105-106`).
- **Already proven against real production renders**: `calibration_report.json` records 4 measurements including `proof_db67b61c.mp4` (a real governed render id, `-25.75` LUFS, PASS) and `pp_governed_video_short_stat.mp4` (`-25.69` LUFS, PASS) alongside one deliberately-silent baseline that correctly FAILs (`no_audio_stream`). This is the exact "deliberately silent-but-voiced test render is caught" behaviour the acceptance target asks for — already demonstrated, just not wired to run automatically on every live render.
- **It runs on the operator's local machine, not in Supabase.** `audio_gate.py` is a plain subprocess-invoking script; it has never executed inside an Edge Function and structurally cannot (§1).

## 3. Hook point inside the pipeline (video-worker v3.17.1, T-inherited from the prior seed)

Confirmed unchanged from the prior scoping seed (`docs/briefs/seeds/video-audio-measurement-capability-scope-v1.md:17-21`), re-verified at current HEAD:

- The rendered mp4 bytes are already in memory at `index.ts:984` (`vidBuf = await (await fetch(renderUrl)).arrayBuffer()`), reused for the presence check (`index.ts:992`), the storage upload (`index.ts:998`), and `file_size_bytes` (`index.ts:1015`). Any additional in-worker byte inspection costs no extra fetch/credit.
- `renderUploadAndLog` composes `render_spec` via `composeRenderSpec(safeQa(() => buildRenderQa({...})), ...)` at two sites — the success log (`index.ts:1004-1028`) and the failure/timeout log (`index.ts:1056-1081`) — both immediately followed by the `write_render_log` RPC call (`index.ts:1029-1036`, `index.ts:1082-1088`). A new `loudness_lufs` input would be threaded into both `RenderQaInput` call sites the same way `cost_present`/`cost_estimated_flag` already are (`qa.ts:43-44,78-79`).
- `submitAndPollCreatomateRender` / `pollRender` (`supabase/functions/video-worker/creatomate_submit.ts:43-53`) is the sibling extraction already used by an out-of-band proof-render harness (`scripts/ws4-d4-kinetic-proof-render.ts`, named at `creatomate_submit.ts:13-17`) — i.e. there is already a precedent for a script outside `index.ts`'s `Deno.serve` listener reusing the identical render-submission logic. A loudness-sweep script following the same import shape (no top-level `Deno.serve`, pure/no side effects) is architecturally consistent with what already exists.

## 4. Wall-clock constraint (why in-EF synchronous measurement is doubly ruled out)

- `POLL_INTERVAL_MS=2500` × `POLL_MAX_ATTEMPTS=48` = 120,000ms — the **hard 2-minute Creatomate render-poll ceiling**, unchanged since introduction (`creatomate_submit.ts:37-38,44-53`; confirmed live-observed at ~128.8–129.2s wall-clock, memory `video-worker-2min-render-timeout-no-retry`). A governed `video_short_stat` render has already been observed timing out against this ceiling on a slow source asset (4× on one draft, `docs/briefs/results/pp-youtube-three-consecutive-governed-stat-videos-result-v1.md`, per that memory).
- This 2-minute figure is the Creatomate-poll ceiling **inside** `renderUploadAndLog`, which itself runs inside the Supabase Edge Function's own wall-clock budget — adding a synchronous network round-trip to an external measurement service on the render's hot path would consume headroom against a ceiling that governed renders are already observed to brush against. **to_be_confirmed**: the exact platform-level Supabase Edge Function wall-clock ceiling (distinct from the 2-min in-code poll loop) was not located in this repo during this design pass — confirm against Supabase's current Edge Function limits before sizing any synchronous option.
- Conclusion: **synchronous, in-render measurement (whether in-EF ffmpeg, or a synchronous call to an external measurement service before `write_render_log`) is not a safe default** given the pipeline already has a documented, real timeout failure mode at this exact ceiling with **no auto-retry** (`video-worker-2min-render-timeout-no-retry` memory — a failed draft is never re-selected). Async is the only design that does not risk trading "no LUFS value" for "no video at all."

## 5. Design options evaluated

| Option | Feasibility | Verdict |
|---|---|---|
| **A — Port ffmpeg/ebur128 into the Deno EF** | Ruled out by the pipeline's own current-code comment (`index.ts:171`) and the prior seed's L2 finding (`video-audio-measurement-capability-scope-v1.md:28`, "No — needs ebur128/ffmpeg; not available in the Deno edge runtime"). A pure-Deno/WASM EBU R128 implementation was not found in this repo and is **to_be_confirmed** as even theoretically viable within EF memory/cold-start limits — not evaluated further here; named for completeness only. | **Rejected as the default** |
| **B — External measurement service, called SYNCHRONOUSLY inside `renderUploadAndLog`** | Technically simple (worker already does one external POST/poll cycle to Creatomate; adding a second HTTP round-trip to a measurement service is the same shape) but stacks new network latency onto a 2-min ceiling the pipeline already fails against (§4) with no retry. | **Rejected — timeout risk** |
| **C — External measurement service, called ASYNCHRONOUSLY by a NEW scheduled sweep** | Reuses the proven `pg_cron` → Edge Function trigger pattern already used for `content_fetch`, `ai-worker`, `publisher`, the hourly planner, etc. (`supabase/migrations/phase2/cron_jobs_snapshot.sql:15-55`). A new low-frequency EF queries recently-succeeded, audio-expected renders with `render_spec.qa.loudness_lufs IS NULL`, calls out to a small always-on ffmpeg-capable HTTP service (hosting choice **to_be_confirmed** — a lightweight container is the shape; the org already runs a Vercel-deployed dashboard, so a Vercel Node function bundling a static ffmpeg binary is one concrete candidate worth evaluating, not yet verified against Vercel's function size/runtime limits), passes it the render's `storage_url`, and writes the returned `{integrated_lufs, true_peak_dbtp}` back. | **Recommended** |
| **D — Manual/operator-run periodic sweep of the existing harness (no new infra)** | Literally re-running `audio_gate.py` against a batch of `storage_url`s downloaded locally, on demand. Zero new infrastructure; proven end-to-end today (§2). Does **not** satisfy "automated" in the acceptance target's own title, and depends on an operator/session being active — not a durable production design. | **Interim bridge only, not the destination** |

**Recommendation**: D as the Phase-0 dark-write proof (cheap, reuses exactly what's already proven), graduating to C as the durable automated design. B stays rejected; A stays out of scope pending someone actually confirming a pure-Deno EBU R128 path exists (unconfirmed either way in this pass).

## 6. Fail-closed rule (design question the task named — proposed answer)

Mirror the audio_gate.py doctrine (uncertain → FAIL) but do **not** conflate "measurement missing" with "measurement says silent" — collapsing those into one null would make a not-yet-swept render indistinguishable from a genuinely-failed one, which is itself an audit gap.

Proposed shape: two fields, not one —
- `loudness_lufs: number | null` — the measured value, or `null` if not yet measured / unmeasurable.
- `loudness_measurement_status: 'measured' | 'pending' | 'unmeasurable' | 'error'` — always set, so "missing" is itself observable rather than silently equivalent to "0 out of 20 render sample happened to include this one."

At **v1 (dark-write, Phase 1 below)**: purely observational — `qa.ts`'s own contract (`qa.ts:6-8`, "NEVER blocks publish or alters render behaviour") argues for landing this the same way `buildRenderQa` itself shipped (QA-VISIBILITY-V0, additive-only) before any later publish-blocking promotion. A genuinely silent-but-voiced render is **already** caught pre-publish by the existing presence-only gate (`index.ts:176-185`, `AUDIO_STREAM_MISSING`, terminal) — loudness measurement adds a *quality floor* on top of an audio track that already exists, which is a materially different (softer, more judgment-laden) gate than "has no audio at all." Promoting `loudness_measurement_status` to a publish-blocking gate is a **separate future T3 PK decision**, not decided here, and should reuse the same phased pattern the presence-only gate itself went through (QA-VISIBILITY-V0 observe-only in v3.1.5 → fail-closed enforcement only later in v3.14.0).

## 7. Rollout plan

1. **Phase 0 — dark-write proof (no pipeline change).** Re-run `_harness/audio_gate_v0/audio_gate.py` against a real 20-render sample (mix of voiced + music-bed renders, pulled by `storage_url` from `ice_ro.render_status`/`ice_ro.draft_status`) exactly as already proven for 4 renders (§2). Manually verify the numbers land in the same class as the existing calibration (`-19` to `-26` LUFS band) before building anything. This directly satisfies the "20-render sample" clause of the acceptance target as a one-off proof, ungated by any code change.
2. **Phase 1 — wire the async sweep (T2 code lane, per the tiering table `...delta-audit-v1.md:542`: "1 design lane (this doc) + 1 wiring lane; could collapse to 1 if the design is simple").** Build the new scheduled EF + measurement-service call + the write-back RPC (§8). Dark/additive: writes `loudness_lufs`/`loudness_measurement_status` into `render_spec.qa`, never blocks. `ef-builder` isolated worktree → hermetic tests → `branch-warden` → external review pinned to hash → PK T3 deploy gate, per the standing CGU orchestration contract.
3. **Phase 2 — promotion decision (separate future PK gate, NOT scoped here).** Once dark-write data exists across a real production window, PK decides whether/how `loudness_measurement_status` becomes publish-blocking, mirroring the presence-only gate's own graduation path.

## 8. Schema touch

- **`render_spec.qa` — additive JSONB keys, no migration needed for the column itself.** `render_spec` is already an untyped JSONB column (`m.post_render_log.render_spec`, confirmed via the column-purpose audit `supabase/migrations/20260502102054_audit_post_render_log_column_purposes.sql:94-95` — deferred LOW-confidence precisely because no fixed schema is enforced) and `qa.ts:17-19` already reserves the `loudness_lufs` name. `RenderQaInput` (`qa.ts:21-45`) and `buildRenderQa` (`qa.ts:54-81`) both gain new optional fields (`loudness_lufs`, `true_peak_dbtp`, `loudness_measurement_status`) — a pure, additive TS change, no DDL.
- **A NEW write-back path IS a migration**, scoped for the Phase-1 apply packet, not created now: a `SECURITY DEFINER`, `service_role`-only RPC mirroring `public.record_music_usage` (`supabase/migrations/20260710121423_create_record_music_usage_rpc.sql:71-119` — the closest existing precedent for "a background process writes a governed fact back onto a render row after the fact") — e.g. `public.record_render_loudness(p_render_log_id uuid, p_loudness_lufs numeric, p_true_peak_dbtp numeric, p_status text)`, jsonb-merging into the existing `render_spec.qa` object rather than overwriting it. Exact signature is a Phase-1 design decision, not fixed here.
- `ice_ro.render_status` currently withholds `render_spec` entirely (`...ice_ro_r0_views_and_confined_role.sql:53`) — a loudness-observability read would need either a new narrow view exposing just the `qa.loudness_lufs`/`qa.loudness_measurement_status` keys, or `execute_sql` (R1) against the jsonb path. **to_be_confirmed** at Phase-1 design time; not decided here.

## 9. Consumers (per the control-tower's ask — design for all three, briefly)

- **M2 (voice acceptance)** needs a *real number*, not presence, to accept a voice — this design's `loudness_lufs` field is the exact input; M2's own acceptance bar (a minimum LUFS floor per client/voice) is M2's decision, not this doc's.
- **M6 (reproducibility bar)** needs the measurement to run across multiple templates/scene-counts consistently — Phase 0's 20-render sample should deliberately include multi-scene renders once they exist, not just the current single-scene stat/kinetic formats, so M6 isn't proving reproducibility on a narrower population than it will actually ship.
- **M12 (rotation proof)** needs per-rotation-slot consistency — once Phase 1 lands, a rotation-pool health check could compare `loudness_lufs` variance across pool members (e.g. B-roll rotation, `broll-rotation-mechanics-and-scope-trap` memory) as a signal that one pool member isn't a quiet outlier; this is a downstream consumption pattern, not built here.
